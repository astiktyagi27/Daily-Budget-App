## 1. Approach
F-002 is the base of Phase 1: it adds the first packages (Riverpod, the preferences store), the bundled fonts, the design tokens, the four themes and the base components. F-003, F-004 and F-005 build on it. The plan follows the design system's Flutter mapping (§8) exactly. Where the plan has to choose something the design does not cover, the choice is stated here.

1. **Packages first (T-101).** Add `flutter_riverpod` 3.4.3 and `shared_preferences` 2.5.6, and switch on `riverpod_lint` 3.1.9. Record the decisions (§4). **No Riverpod code generation** (reason in §4).
2. **One preferences store for the whole phase (T-102), behind an interface in `data/`.** F-002 (theme), F-004 (hint flags) and F-005 (tour and onboarding flags) share it (phase overview). The code above it never sees the plugin:
   - `PreferencesStore` (interface): sync `readString` / `readBool`, async `writeString` / `writeBool` / `remove`. The reads are sync because every value is loaded once before the first frame, so the first frame is already in the saved theme with no flash (AC-7).
   - `SharedPreferencesStore`: the only file that imports `shared_preferences`. It uses **`SharedPreferencesWithCache`** with an `allowList` of the app's keys. The plugin's README marks the legacy `SharedPreferences` API "will be deprecated in the future" and recommends the new APIs. `WithCache` gives sync reads after one async `create()`, which is exactly what a first frame without a flash needs. On Android it uses Jetpack DataStore, the platform-recommended store.
   - `InMemoryPreferencesStore`: a plain map. It is used **as the fake in tests** and also **as the runtime fallback** when the plugin cannot be opened (AC-8; F-004 AC-12; F-005 AC-15). The app then works for the session and falls back to defaults on the next launch.
   - Every read is wrapped: a missing key, an unreadable value or a value of the wrong type returns `null`, so the caller uses its default. Every write catches errors and returns `false`. The in-memory app state has already changed, so the session keeps working. Nothing is logged: there is no logger in Phase 1, and these values are not personal data anyway.
   - Adapter tests run in plain `flutter test` with the platform interface's `InMemorySharedPreferencesAsync`. No device and no native build are needed, so most of the work and all automated tests can go ahead even if the Owner's Windows Developer Mode stays off (§7).
3. **Fonts bundled (T-103).** These are the official upstream files, pinned by release or commit and by SHA-256, plus their OFL texts registered in `LicenseRegistry`. A **permanent automated test** reads the bundled Plex files and checks the `cmap` table for U+20B9 (₹) and the `GSUB` table for `tnum`. That is the design system §4.1 check, run on every test run rather than once (§2, T-103). `google_fonts` is not used.
4. **Tokens as code (T-104).** `BudgetColors` (a `ThemeExtension` with `const light` / `dark` / `dim` instances, hex values from design §2), `BudgetText` (a `ThemeExtension` with the money and heading styles), and the const classes `BudgetSpacing`, `BudgetRadii`, `BudgetMotion`, plus `BudgetElevation` (a `ThemeExtension`). All follow design §8.4. A unit test computes the WCAG ratio for **every pair in design §3** from these constants (design §8.5), so a careless edit to a hex value fails the build.
5. **`ThemeData` builder (T-105).** One function `buildBudgetTheme(BudgetColors colors, Brightness b)` builds the `ColorScheme(...)` field by field (design §8.2, not `fromSeed`), the text theme (design §4.2 / §8.3), the component themes (design §8.3) and the extensions. Three themes come out of it: Light, Dark and Dim. The mapping from the user's choice follows design §8.1:

   | Choice | `themeMode` | `theme` | `darkTheme` |
   |---|---|---|---|
   | Auto | `system` | Light | Dark |
   | Light | `light` | Light | Dark |
   | Dark | `dark` | Light | Dark |
   | Dim | `dark` | Light | Dim |

   The mapping always fills `theme` and `darkTheme` and only switches `themeMode` / `darkTheme`. `MaterialApp`'s built-in theme animation (`themeAnimationDuration`, set to `BudgetMotion.base`, 200 ms, and 0 when Remove animations is on) cross-fades through the extensions' `lerp`. Auto follows the phone live by itself: `ThemeMode.system` rebuilds on `platformBrightness` changes (AC-4).
   **System bars (AC-18):** `MaterialApp.builder` wraps every route in an `AnnotatedRegion<SystemUiOverlayStyle>` derived from the active theme's brightness. It sets a transparent status bar and nav bar, dark icons on Light, and light icons on Dark and Dim. This covers the onboarding pages, which have no `AppBar`.
6. **Test harness + token guard (T-106).** Shared helpers in `test/helpers/`:
   - `pumpBudgetApp` / `pumpBudgetWidget`: `ProviderScope` with an `InMemoryPreferencesStore`, theme case, screen size and text scale.
   - `ThemeCase` variant: **Light, Dark, Dim, Auto-system-light, Auto-system-dark**, the F-002 definition of "all four themes".
   - `expectAccessible()`: `textContrastGuideline`, `androidTapTargetGuideline` and `labeledTapTargetGuideline`, plus "no exception / no overflow".

   Every Phase 1 screen test uses these. An architecture test (like F-001's domain guard) fails if `lib/features/` contains `Color(`, `Colors.`, `fontFamily:`, `GoogleFonts` or a raw hex literal `0xFF…` (AC-9).
7. **Base components (T-107)** in `core/widgets/`: `BudgetButton` (`.primary`, `.secondary`, `.text`, `.destructive`), `BudgetCard`, `BudgetListRow` (leading / label / description / trailing slots; F-004 adds the (i) slot to it in T-116), and `BudgetTextField` (label above, description, `₹` prefix option, error with icon + text, per design §7.3 and help-pattern §9). Each one is styled only through the theme and the extensions. Buttons use `FilledButton` / `OutlinedButton` / `TextButton` with themed styles, so focus, pressed and disabled states come from Material state handling.
8. **Theme choice state (T-108).** `ThemeChoice` (`auto`, `light`, `dark`, `dim`) is a pure-Dart enum in `domain/preferences/`. It carries its storage value and a tolerant `fromStorage(String?)` that returns `auto` for null or unknown values such as `"blue"` (AC-8). `ThemePreferenceRepository` (`data/`) reads and writes it through the store. `themeChoiceProvider` (a Riverpod `Notifier<ThemeChoice>`) reads the value synchronously in `build()`. `select()` sets the state **first** and then awaits the write, so the change is instant and survives a failed write for the session (AC-5, edge case "store fails"). Fast repeated taps simply set state in order, and the last write wins in both memory and storage (TC-002-33). `main()` becomes: `WidgetsFlutterBinding.ensureInitialized()` → `registerFontLicenses()` → `await openPreferencesStore()` (falls back to in-memory on any error) → `runApp(ProviderScope(overrides: [preferencesStoreProvider.overrideWithValue(store)], child: const DailyBudgetApp()))`.
9. **Theme row + picker (T-109)** follow `docs/design/screens/settings.md`. The row is a `BudgetListRow` with the F-004 label + description + (i). Its description shows the current choice. Tapping the row opens a bottom sheet with a `RadioGroup<ThemeChoice>` of four option rows (Flutter 3.35+ API; the `groupValue` on each `Radio` is deprecated). A selected row has a dot, a check icon and a heavier label, so the state is not shown by colour alone. Picking an option **applies it live and keeps the sheet open**. `Done`, swipe down, a scrim tap or back closes the sheet. TalkBack hears "Theme changed to <name>" through `SemanticsService.sendAnnouncement` (the non-deprecated API). This task can only run after the F-003 Settings tab (T-113) and the F-004 help row (T-116, T-117) exist.

**Alternatives rejected**
- *`google_fonts` with runtime fetching off*: it is still a network-capable dependency, and it would need an explicit "no fetch" config to prove AC-15. Plain bundled assets are simpler and provably offline.
- *`ColorScheme.fromSeed`*: it generates tones we did not choose and breaks the contrast table. Design §8.2 says to use the constructor.
- *Legacy `SharedPreferences` API*: deprecation is announced, and its `flutter.` key prefix makes later migration fiddly. *`SharedPreferencesAsync`*: every read is async, so the first frame would have to wait on a future per value or show a flash.
- *Storing preferences in the Phase 2 Drift database*: the database does not exist in Phase 1, and the phase overview says these are simple preferences, not money data.
- *A file in app documents via `path_provider` + JSON*: that is also a plugin (the same build constraints), and we would have to write our own atomic writes and corruption handling. `shared_preferences` already does this and is maintained by the Flutter team.
- *`hive_ce` / `isar` for three flags*: a database engine for a few booleans is speculative weight (STANDARDS §1).
- *`ThemeMode` plus a separate "isDim" flag in state*: one enum with an exhaustive `switch` is clearer, and the compiler checks that every case is handled.

## 3. Data model / database changes
No database. These are app preferences in Android DataStore through `shared_preferences` (`SharedPreferencesWithCache`). They are not money data, and they never leave the phone. Keys are defined once in `data/preferences/preference_keys.dart`. The `allowList` is built from that same list, so a key that is not listed cannot be read or written by accident.

| Key | Type | Values | Default when missing or unreadable | Owner |
|---|---|---|---|---|
| `theme.choice` | String | `auto` · `light` · `dark` · `dim` | `auto` | F-002 |
| `onboarding.tour_seen` | bool | true/false | false | F-005 |
| `onboarding.finished` | bool | true/false | false | F-005 |
| `hint.<tab>.v1.seen` (4 keys: `home`, `dashboard`, `transactions`, `settings`) | bool | true/false | false (hint shows) | F-004 |

Clearing app data or reinstalling removes all keys, which gives the same result as a fresh install (expected; D-003).
